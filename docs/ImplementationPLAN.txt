# Local Football Tournament Auction — Master Implementation Specification

I want you to build a production-quality web application for conducting local football player auctions, inspired by the workflow of an IPL-style auction.

This document is the source of truth for the application. Read the entire specification before making architectural decisions.

Do not attempt to implement the entire application in one uncontrolled pass. Work milestone-by-milestone, keep the application runnable after every milestone, run the relevant tests before considering a milestone complete, and avoid unnecessary architectural complexity.

---

# 1. Product Goal

The application will allow tournament organizers to:

1. Create a tournament.
2. Configure auction rules for that tournament.
3. Create participating teams.
4. Give each team a purse/budget.
5. Create ordered sets of players.
6. Add players and assign them to sets.
7. Configure player base prices.
8. Validate that the tournament is ready for auction.
9. Start a live auction.
10. Randomly order players within each set.
11. Reveal players one at a time.
12. Mark players as sold or unsold.
13. When sold, record the winning team and sale price.
14. Automatically calculate team expenditure, remaining purse, squad size and auction constraints.
15. Continue through every set.
16. Optionally re-auction unsold players.
17. Complete the tournament auction.
18. Generate attractive statistics and reports after the auction.
19. Provide a separate read-only live/projector screen that updates in real time.

The app should be reusable for multiple tournaments.

Tournament-specific rules must NEVER be hard-coded into the application.

---

# 2. Important MVP Assumption

The application does NOT conduct bidding electronically in V1.

Bidding happens physically/offline between team owners.

The application is operated by an auctioneer/admin who records the result.

Example:

Player appears on screen.

Physical bidding occurs.

Auctioneer then selects:

Winning Team:
Falcons FC

Final Price:
₹8,500

and presses:

SOLD

Alternatively:

UNSOLD

Electronic bidding from team-owner phones can be considered in a future version, but should NOT be implemented in the MVP.

Keep the architecture simple.

The system should essentially be:

React
↓
ASP.NET Core API
↓
Entity Framework Core
↓
PostgreSQL

Real-time updates:

ASP.NET Core
↓
SignalR
↓
React clients

DO NOT introduce:

- Microservices
- Kubernetes
- Event buses
- Redis unless a real need appears
- CQRS frameworks just for the sake of CQRS
- MediatR unless it provides an actual benefit
- unnecessary repository abstractions over EF Core
- complicated serverless infrastructure
- Redux unless the application genuinely needs it

This is a tournament auction application, not a banking platform.

Prioritize correctness, maintainability and simplicity.

# 5. Source of Truth

PostgreSQL is the authoritative source for:

- auction state
- team purse calculations
- player sale results
- squad sizes
- current set
- current player
- randomized player order
- tournament configuration

Never make React client state authoritative for auction information.

If the browser refreshes or the laptop restarts, reopening the application must reconstruct the complete current auction state from PostgreSQL.

# 17. Random Player Selection

This is extremely important.

DO NOT randomly select a new player in the React browser every time NEXT PLAYER is clicked.

When a player set begins:

1. Fetch all eligible players in that set.
2. Randomize them server-side.
3. Persist the randomized order as AuctionLots with DrawPosition.
4. Commit this order to PostgreSQL.
5. Only then reveal the first player.

Example stored queue:

1 Player 38
2 Player 12
3 Player 7
4 Player 25
5 Player 3

The future order must not be shown to normal users.

Once generated, the order must NEVER change because of:

- refresh
- reconnect
- browser restart
- backend restart
- another admin opening the auction

The system simply reveals the next PENDING lot ordered by DrawPosition.

This prevents duplicated players and accidental re-randomization.

# 18. Auction State Machine

The auction should have explicit legal state transitions.

Tournament:

DRAFT
→ READY
→ LIVE
→ COMPLETED

Auction:

READY
→ LIVE
↔ PAUSED
→ COMPLETED

Player lot:

PENDING
→ ON_AUCTION
→ SOLD

or:

PENDING
→ ON_AUCTION
→ UNSOLD

Invalid transitions must be rejected server-side.

Examples:

Cannot sell a PENDING player.

Cannot sell an already SOLD player.

Cannot reveal another player when one is currently ON_AUCTION.

Cannot start the second set while the first still has unresolved players unless an explicitly designed admin override exists.

# 20. Selling a Player

When the auctioneer selects:

Winning Team:
Falcons

Final Price:
₹8,500

and presses SOLD:

the server must validate everything before committing.

Validation should include:

- auction is LIVE
- lot is ON_AUCTION
- player has not already been sold
- selected team exists
- selected team belongs to tournament
- team has not reached maximum squad size
- price is at least the player's base price
- price respects configured bid rules
- team has sufficient remaining purse
- purchase does not violate required minimum-squad reserve

Only after validation succeeds should the server transaction commit the result.

---

# 21. Purse Calculations

Do not manually maintain remaining purse.

For each team:

TotalSpent =
sum of FinalPrice from SOLD lots won by the team

RemainingPurse =
InitialPurse - TotalSpent

CurrentSquadSize =
number of SOLD players belonging to team

Expose these calculations through the backend.

The UI can display the returned values but should not be responsible for authoritative calculations.

---

# 22. Minimum Squad Reserve

The application must help prevent a team from spending so much money that it cannot theoretically reach its minimum required squad size.

Example:

Team purse remaining:
₹15,000

Current squad:
9

Minimum squad:
12

Minimum acquisition price:
₹1,000

Players still required:
3

Required reserve:
₹3,000

When considering purchasing the current player, calculate squad size AFTER the potential purchase.

remainingPlayersRequired =
max(0, minimumSquadSize - (currentSquadSize + 1))

reserveAfterPurchase =
remainingPlayersRequired × minimumAcquisitionPrice

maximumAllowedPurchase =
currentRemainingPurse - reserveAfterPurchase

Reject a purchase above the allowed maximum.

Return a meaningful validation message such as:

"Falcons FC cannot spend ₹14,000 on this player. The maximum allowed purchase is ₹13,000 because ₹2,000 must remain available to satisfy the minimum squad requirement."

Do not merely return HTTP 400 with no useful explanation.

Maximum squad = 16

# 24. Unsold Players & Mandatory Final Unsold Round

When a player receives no bids, the auctioneer presses UNSOLD.
Store the attempt as UNSOLD.

### Mandatory Final Unsold Round Rule:
After ALL normal player sets have finished, if there are unsold players:
A single FINAL UNSOLD ROUND is MANDATORY before normal auction completion.
If there are no unsold players, the tournament proceeds directly to auction completion checks.

When the Final Unsold Round begins:
1. Collect all players whose latest normal auction result is UNSOLD.
2. Create a new AuctionLot for each unsold player with AttemptNumber = 2.
3. Base price remains unchanged during the final unsold round.
4. Randomize the unsold players server-side once and persist with DrawPosition (future order is never exposed publicly).
5. Reveal players one by one using standard auction workflow.
6. With SellAllPlayers disabled (the default), a player unsold in Attempt 2 becomes FINAL_UNSOLD. No third attempt occurs in this mode.

### Configurable Sell All Players Extension:
The owner may enable SellAllPlayers in Auction Rules & Purse while the tournament is DRAFT. It defaults to false for existing and new tournaments. This does not make the initial unsold round optional.
With this setting enabled, launch the initial unsold round after all normal sets finish. Whenever every lot in an unsold round is resolved, automatically queue a new round containing only players whose latest result remains UNSOLD. Continue with AttemptNumber 3, 4, and so on until every registered player is SOLD. Each round has a persisted randomized draw; the auctioneer still reveals and resolves each player explicitly.
Keep the base price unchanged and retain every attempt and round-start audit record. Console, projector, public views, and history display the current round. Auction completion, including an owner override, is blocked until all players are SOLD.
Existing bid, purse reserve, and maximum squad rules still apply. Preflight checks full-pool squad capacity and starting purse affordability when this setting is enabled. Organizers must configure adequate capacity and manage spending throughout the auction.

Example history:
Player A:
Attempt 1 → UNSOLD
Attempt 2 → SOLD → Falcons → ₹2,500
Both attempts remain in the audit history.

# 26. Auction Completion

Before allowing normal completion:
1. Verify that all normal sets are complete.
2. If any unsold players exist, verify that the Final Unsold Round has been conducted and all eligible unsold players have received their second attempt. Auction completion is blocked if unresolved eligible unsold players remain.
   When SellAllPlayers is enabled, every registered player must instead be SOLD; unresolved players continue into successive unsold rounds and no completion override bypasses this requirement.
3. Validate squads against MinimumSquadSize.

Example:

Falcons      12 / 12 ✓
Warriors     14 / 12 ✓
United       11 / 12 ✗

If a team is below the minimum:
show a blocking warning.

If real-world circumstances require completion anyway, an OWNER may eventually be allowed to override this rule, but:
- require a written reason
- record the reason in audit history
- clearly mark the auction as completed with warnings

Do not silently ignore the problem.

# 29. Concurrency and Double-Click Protection

This is a critical requirement.

Possible scenario:

The auctioneer accidentally double-clicks SOLD.

Or:

Two admins have the auction console open.

Both must NOT be capable of selling the player twice.

Auction mutation operations should execute in a PostgreSQL transaction.

Protect relevant rows from concurrent modification.

Use optimistic concurrency/version checks and/or PostgreSQL row locking as appropriate.

The API request should include the current LotId.

If the first request has already completed the lot, the second request must fail safely with HTTP 409 Conflict or equivalent.

Where useful, add database constraints/partial unique indexes to protect against impossible states.

Correctness must not depend on React disabling a button quickly enough.

# 56. Rules for Working on This Project

When implementing any milestone:

1. Inspect the existing code before changing architecture.

2. Do not rewrite working components simply because another architecture looks more elegant.

3. Explain any necessary architectural deviation from this document.

4. Use database migrations for schema changes.

5. Keep business logic out of React components.

6. Keep business logic out of ASP.NET controllers where practical.

7. Keep PostgreSQL authoritative.

8. Never use floating point for money.

9. Never trust client-side purse calculations.

10. Never regenerate a set's random player order after the set begins.

11. Never permit two active players simultaneously.

12. Never permit the same auction lot to be completed twice.

13. Never silently delete auction history.

14. Never directly overwrite important financial results without creating an audit entry.

15. Every financial/state-changing backend operation must perform authorization and validation.

16. Use transactions for auction mutations.

17. Return useful error messages.

18. Run relevant tests after each implementation task.

19. Keep the application runnable after each milestone.

20. Prefer simple, readable solutions over unnecessarily abstract patterns.
